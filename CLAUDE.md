## Regras que já causaram bugs reais (não repetir)

1. **`API_URL` ≠ `SITE_URL`.** `API_URL` é só o backend de dados; nunca usar para montar link
   compartilhável (WhatsApp, Stories). Link compartilhável é sempre `SITE_URL`. `index.html` e
   `admin.html` têm que apontar para a mesma `API_URL` — trocar só em `common.js`.
2. **Toda mensagem enviada ao cliente/candidato (WhatsApp etc.) tem que ter o endereço completo e
   clicável** (ex. `https://tenkitermodas.com.br/treinamentos.html`), nunca só o nome do arquivo. "Tem
   que facilitar" — a pessoa só clica.
3. **Busca sempre ignora filtros ativos.** Quando há termo de busca, ele busca em TUDO,
   independente de status/etapa/agenda selecionados — nunca ANDar busca com filtro.
4. **Nunca dumpar JSON cru na UI.** Erros/respostas estruturadas (ex. `errosDetalhados` dos
   testes) sempre renderizados como cards legíveis, nunca como texto JSON escapado.
5. **Convenção de versão dos `.gs.txt`**: ao editar um backend, sempre `git mv` para o próximo
   número de versão no nome do arquivo, E atualizar o comentário de cabeçalho E o campo
   `versao` retornado por `doGet` com `action=='versao'` — os três têm que ficar sincronizados.

## Deploy — automático pelo GitHub

- **Regra (Pablo, 17/10/2026)**: deploy é feito por você, direto pelo GitHub, sem pedir confirmação e sem enrolar. Não existe mais restrição de "deploy manual pelo Pablo" para o frontend. Sempre que houver acesso ao GitHub, fazer o deploy assim que o trabalho estiver pronto e testado.
- **Regra (Pablo, 18/10/2026)**: não existe nenhuma instrução de deploy manual no Render (nem pelo MCP `mcp__Render__*`, nem pelo painel, nem pela API). O único caminho de publicação é o `deploy.yml` no merge na `main`. Se o deploy falhar, corrigir pelo GitHub (workflow/PR ou reverter a `main`).
- **Ponto de restauração obrigatório antes de cada merge na `main`**: criar uma branch `backup/pre-<tema>-<data>` apontando para o commit atual da `main`. Assim qualquer deploy pode ser desfeito rapidamente.
- **Branches (revisão de 18/10/2026, 2ª)**: a sessão do Claude NÃO consegue apagar branch (o proxy do GitHub dá 403 em `DELETE git/refs` e em `git push --delete`). O Pablo AUTORIZOU (18/10/2026: "apague branches que não sirvam mais") o workflow `.github/workflows/limpar-branches.yml`: ele usa o `GITHUB_TOKEN` do próprio GitHub e só apaga o que está em `.github/limpar-branches.txt` (`<nome><TAB><sha da ponta>`; só apaga se a ponta de hoje é aquele sha; nunca `main`, protegida ou `restauracao-*`; o sha de cada apagada fica no log para recriar com `git push origin <sha>:refs/heads/<nome>`). Dispara quando a lista muda na `main` (ou manualmente digitando APAGAR). **Depois de rodar, esvazie a lista** (PR de docs). Branch nova que o Pablo mandar apagar = acrescentar a linha na lista, nunca apagar por outro caminho. Nunca prometa que apagou sem conferir: `gh api repos/pablofonteneleadv/tenkiter-catalogo/branches --paginate --jq '.[].name'`. A criação de ref pela API REST é bloqueada — use `git push origin <sha>:refs/heads/<nome>`.
- **Fluxo padrão (frontend)**:
  1. Criar o ponto de restauração (`backup/pre-...`).
  2. Fazer o PR (ou usar o PR existente) e aguardar o check "Portão de qualidade" ficar verde.
  3. Fazer o merge na `main`. O push na `main` dispara `.github/workflows/deploy.yml`, que publica o site sozinho, acompanha até "live" e confirma o commit em `/version.json`.
  4. Conferir no site publicado (`https://tenkiter-catalogo.onrender.com/<arquivo>`) com `grep` por uma string nova do commit.
  5. Se der errado: reverter com novo commit na `main` ou restaurar a partir do `backup/pre-...`.
- **Cópia dos .md (pedido do Pablo, 17/10/2026)**: a cada atualização, além do deploy automático, gerar um zip com os `.md` alterados (sempre `CLAUDE.md` e `okou.md`) em `entregas/okou-md-<data>.zip` e enviar ao chat (neste ambiente: `SendUserFile`; no ambiente Okou: `okou web upload-file -f <zip> --json`). O Pablo guarda essa cópia; outra cópia vai ao cofre em `md/` (seção v4.21). Não precisa subir arquivo manualmente no GitHub.
- **Deploy automático autorizado**: o merge na `main` publica sozinho pelo `deploy.yml`. Não pedir confirmação. Verificar o término pelo `gh run list --branch main` e conferir `https://tenkiter-catalogo.onrender.com/version.json` (campo `commit`).
- **Workers Cloudflare (`tenkiter-ig`, `tenkiter-midia`, `tenkiter-og`)**: o `deploy.yml` chama o `workers.yml` e publica os três a cada merge na `main` (e `Verificar os 3 Workers publicados` confere `modified_on`). Isto só funciona desde o PR #34 (18/10/2026): antes, com `skip_ci`, os jobs `Publicar …` ficavam *skipped* em silêncio e NENHUM Worker era publicado pelo deploy. Depois de todo merge, olhe os jobs `Publicar tenkiter-*`: têm que estar `success`. Disparo manual de emergência: Actions → Workers (Cloudflare) → Run workflow. Os `publicar.py` de cada pasta ficam só como reserva.
- **Bateria final**: a bateria completa (`tests/rodar_tudo.py` com `TK_BASE=https://tenkiter-catalogo.onrender.com/`) roda só quando o Pablo pedir, depois que o site já estiver atualizado.
- **Backend (Apps Script)**: **não pode ser deployado por automação** — precisa que o Pablo cole
  manualmente o `.gs.txt` MAIS NOVO (o do cofre, ver "Estado atual" no topo) no editor do Apps Script e clique em "Nova versão" (Gerenciar
  implantações → editar → Nova versão). Depois que ele confirmar, validar com:
  - `curl` em `?action=versao` esperando a versão nova (GET funciona normal com curl).
  - Para testar ações via **POST**, curl com User-Agent padrão cai na proteção
    anti-bot do Google (HTTP 405 + página de erro do Google Drive). Usar Python

## Link e miniatura do produto

- Link público da peça: **sempre** `linkProduto(p)` (common.js) = `SITE_URL + 'p/<código>'` (com a foto/vídeo escolhido: `linkProduto(p, n)` = `.../p/<código>?f=n`, ver seção "Foto escolhida" no fim). Nunca montar a partir de
  `API_URL` — o `?action=share` do Apps Script devolve HTML dentro de um iframe do Google, o WhatsApp não lê as meta
  tags `og:*` dali e a mensagem mostrava o endereço do script sem miniatura (bug real, não repetir).
- Miniatura **por produto**: Cloudflare Worker `tenkiter-og` (código em `og-worker/worker.js`, endereço
  `https://tenkiter-og.distkrpconfeccoes.workers.dev`) devolve HTML com `og:*` em `/p/<código>` e redireciona a pessoa para
  `?c=<código>`. No Render existe a regra Rewrite `/p/*` -> `<worker>/p/*` (confirmado: faz proxy, não redireciona). Se mudar
  o código do Worker, publicar de novo na Cloudflare (painel ou API). `og-service/` (Node) é alternativa antiga, não usada. O Worker é **v2 e está PUBLICADO desde 10/10/2026** (publicado pela API da Cloudflare, `og-worker/publicar.py`; JSON-LD, `/sitemap.xml`, `/feed.csv|xml`, `/lista.json`) — guia de publicação em `og-worker/LEIA-ME.md`. **Regras Rewrite no Render (criadas em 10/10/2026 pela API do Render):** `/p/*`, `/feed.csv`, `/feed.xml`, `/sitemap.xml` → mesmo caminho no Worker (rotas e cabeçalhos do Render só se mexem por API REST — `https://api.render.com/v1/services/<id>/routes` — ou pelo painel; o MCP do Render não tem isso).
  `index.html` mantém `og:image` genérico (`og-banner.jpg`) para o link da loja em si.

## v3.4 — foto escolhida no compartilhar e categorias do painel (backend 3.2)

## CI/CD otimizado — decisão registrada em 17/10/2026

**Objetivo do Pablo:** parar de repetir a bateria gigante de testes a cada merge/deploy, reduzindo o tempo de espera sem desativar verificações importantes.

- `.github/workflows/ci.yml`: CI curto para PRs e deploys; mantém scan de segredos, sintaxe JS/HTML, configuração dos Workers e sintaxe dos scripts. O modo rápido roda os testes funcionais unitários dos Workers de mídia, Instagram e canal, sem instalar Chromium.
- **Bateria completa:** `tests/rodar_tudo.py` com Playwright, acessibilidade e jornadas roda por agendamento diário ou manualmente em **Actions → CI → Run workflow → suite=completo**. Não deve ser repetida em etapas isoladas que o próprio executor já inclui.
- **Deploy:** `deploy.yml` chama o CI reutilizável no modo rápido. O CI não tem gatilho de `push: main`, evitando que o mesmo commit dispare um CI separado e outro dentro do deploy.
- **Workers Cloudflare:** publicação automática é orquestrada pelo `deploy.yml`; `workers.yml` recebe `skip_ci: true` quando chamado pelo deploy, porque o commit já passou pelo portão. Execução manual de `workers.yml` continua executando o CI rápido.
- **Portão obrigatório:** manter exatamente o nome `Portão de qualidade`, pois pode estar configurado como status check obrigatório da proteção de `main`. Não mudar a semântica do job sem conferir a proteção de branch.
- **Mudanças de alto risco:** antes de publicar alterações amplas em catálogo, cadastro/admin, autenticação, Apps Script, acessibilidade ou fluxos críticos, executar a bateria completa manualmente quando viável. O modo rápido não substitui a cobertura completa.
- **Sem falhas silenciosas:** não adicionar `continue-on-error: true` a testes bloqueantes sem justificar/documentar a limitação.
- A bateria completa fica agendada para 03:00 UTC (00:00 em Fortaleza). **Primeira execução agendada (18/10/2026, ~24 min) terminou em FALHA ("exit code 1")**. O log não é baixável pelo proxy da sessão do Claude; a causa mais provável é que `backend_gs.js`, `backend_contas.js` e `backend_func.js` leem o `.gs.txt` do backend, que NÃO está no repositório público (então no GitHub nunca poderiam passar). Correção (PR de 18/10/2026): `tests/rodar_tudo.py` PULA esses testes quando não há `.gs.txt` (imprime a lista dos pulados e um `::warning`), inclui na bateria os testes novos que estavam de fora (`postagens_fila/colagem/v425/avulsas/texto_foto`, `selecao_vida/botoes`, `pendente_flutuante`, `foto_ia`, `worker_canal`) e, no GitHub, cada teste que falha vira uma anotação `::error` legível pela API (`check-runs/<id>/annotations`) — a noite de 19/10/2026 mostra o que mais cai, se cair.
- A otimização do CI (PR #16) já foi revisada e mesclada. O PR #34 (18/10/2026) corrigiu o `workers.yml` com `skip_ci` (os Workers não eram publicados pelo deploy). **Mudanças futuras em workflow**: continuam por branch e PR, com o diff revisado e os checks verdes antes do merge.
